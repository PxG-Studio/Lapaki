## Purpose and Scope

This document provides the authoritative compliance annotation for every node in the Health Data Architecture Framework Mind Map (`03-mindmap.md`). It is the primary reference for:

- **Internal auditors** conducting HIPAA Security Rule risk assessments (45 CFR §164.308(a)(1))
- **External auditors** performing COBIT 2019 maturity assessments
- **Privacy Officers** responding to HHS Office for Civil Rights (OCR) desk audits
- **IRB administrators** reviewing data governance adequacy
- **Information Security Officers** implementing NIST SP 800-53 Rev. 5 controls
- **Research compliance officers** preparing NIH Data Management and Sharing Plan certifications

For each node in the mind map, this document provides: the controlling standard citation (with section-level precision), the COBIT 2019 management objective the node maps to, the risk if the node is misconfigured or uncontrolled, and the specific audit evidence required to demonstrate compliance during an examination.

The document is organized in two parts:
1. **Master Compliance Reference Table** — a comprehensive matrix covering all nodes
2. **Detailed Prose Notes by Branch** — extended analysis of each major branch

## Part II: Detailed Prose Notes by Branch

### Branch 1: Operational & Source Systems — Extended Compliance Analysis

The Operational & Source Systems branch represents the data generation layer — the environmental stratum where PHI is first created, captured, and transmitted. From a HIPAA Security Rule perspective, this branch is governed primarily by the Technical Safeguards standard (45 CFR §164.312), which requires covered entities to implement technical policies and procedures for electronic PHI (ePHI) access control (§164.312(a)(1)), audit controls (§164.312(b)), integrity controls (§164.312(c)(1)), authentication (§164.312(d)), and transmission security (§164.312(e)(1)).

**The EHR system** is both the richest source of clinical data and the highest-risk system in the enterprise. The HIPAA Omnibus Rule (78 Fed. Reg. 5566, January 25, 2013) and the ONC 21st Century Cures Act Final Rule (85 Fed. Reg. 25642, May 1, 2020) together mandate that EHR systems support HL7 FHIR R4 API access without special effort or fees (Information Blocking prohibition, 45 CFR Part 171). The Information Blocking Rule at 45 CFR §171.301 prohibits any practice that is likely to interfere with, prevent, or materially discourage access, exchange, or use of electronic health information — with civil monetary penalties up to $1,000,000 per violation for health IT developers and networks, and disincentives for hospitals and clinicians. Organizations must carefully audit their EHR configurations to ensure that legitimate research data access does not inadvertently constitute information blocking.

**HL7 v2 messaging** remains the dominant real-time interface format in healthcare despite FHIR's growth, and it represents a significant security risk because it has no native encryption or authentication mechanism. Organizations must ensure that all HL7 v2 feeds are carried over encrypted transport (TLS 1.3, minimum — deprecated versions TLS 1.0 and 1.1 must be disabled per NIST SP 800-52 Rev. 2), dedicated network segments, or VPN tunnels. NIST SP 800-53 Rev. 5 SC-8 (Transmission Confidentiality and Integrity) is the controlling security control.

**Claims and payer data** introduce a particularly complex compliance overlay. CMS Research Data Assistance Center (ResDAC) data — Medicare and Medicaid claims — are subject to CMS-specific DUAs that impose requirements stricter than baseline HIPAA: data cannot be used for commercial purposes, must be stored in a secure environment meeting CMS specifications, must be destroyed or returned at the end of the study, and CMS must be notified of any security incident. Non-compliance can result in fines of up to $250,000 and 10-year debarment from future CMS data access — consequences that dwarf most HIPAA CMPs in practical impact.

The **Operational Self-Service** node represents the business intelligence democratization of operational data. The critical compliance requirement here is that self-service access must not enable research without IRB review. RBAC controls must ensure that users cannot extract record-level PHI through BI tools, and row-level security must enforce the Minimum Necessary standard (45 CFR §164.502(b)) automatically. Data Loss Prevention (DLP) tools should be implemented at the self-service export layer to prevent unauthorized data exfiltration.

### Branch 2: Internal Research Environment — Extended Compliance Analysis

The Internal Research Environment branch is the core of the research data governance infrastructure. It is where the transformation from operational data to research-ready data occurs — and where the greatest concentration of compliance risk exists because data flows between the operational (HIPAA-covered) and research (Common Rule-covered) domains.

**The Integrated Research Warehouse (IRW)** is subject to a dual regulatory regime: HIPAA (as a system that stores ePHI) and the Common Rule (45 CFR Part 46) (as the repository used for research with human subjects). The IRW must have a current, HIPAA-compliant risk analysis (45 CFR §164.308(a)(1)) that identifies all threats to ePHI confidentiality, integrity, and availability. The IRW risk analysis should specifically address: unauthorized insider access (the most common HIPAA breach type), SQL injection and database vulnerabilities, backup and recovery failures, and cloud migration risks if applicable. The risk analysis must be documented, reviewed, and updated when operations or the environment change materially.

**Master Patient Index (MPI) integrity** is a patient safety issue, not merely a data governance issue. When two patient records are incorrectly merged (a "false positive" match), the resulting longitudinal record will contain data from two different patients — a condition that can cause clinical harm (e.g., a researcher studying medication safety uses merged records that contain another patient's adverse event). MPI governance must include: documented matching algorithm parameters, threshold tuning history, periodic duplicate pair audits by clinical reviewers, and a formal un-merge process. The MPI access control matrix should restrict MPI administration to an extremely limited set of named individuals.

**De-identification certification** deserves extended attention because it is the most legally consequential technical determination in the framework. The Safe Harbor method at 45 CFR §164.514(b)(2) provides a "safe harbor" — if all 18 identifier types are genuinely removed or generalized and the covered entity has no actual knowledge that residual information could identify an individual, the data is legally de-identified and HIPAA no longer applies. However, "no actual knowledge" is a subjective standard, and organizations should implement automated PII scanning (e.g., using regular expression libraries for SSN patterns, date patterns, name entity recognition) as a backstop to manual de-identification processes.

The Expert Determination method at §164.514(b)(1) is scientifically more rigorous but legally riskier — the organization is affirmatively certifying that re-identification risk is "very small" based on statistical analysis. The standard does not specify a numerical threshold; the OCR's November 2012 Guidance suggests considering both the probability that information could be used to identify an individual and the probability that such identification would be attempted. Organizations should document both dimensions. k-anonymity (Sweeney, 2002) with k≥5, l-diversity (Machanavajjhala et al., 2007), and t-closeness (Li et al., 2007) are commonly applied techniques, but none is universally sufficient — the statistician must select techniques appropriate to the specific dataset's quasi-identifier profile.

### Branch 3: External Collaborative Research — Extended Compliance Analysis

The External Collaborative Research branch governs data flows that cross institutional boundaries — the highest-risk category of data movement in the framework. Every external data share requires a legal instrument (BAA, DUA, or Research Collaboration Agreement), an IRB authorization, and technical safeguards applied at the egress point.

**PCORNet participation** carries specific obligations that go beyond baseline HIPAA. The PCORNet Network Principles require that contributing sites: maintain CDM data quality at or above network thresholds (flagged sites are suspended from distributed queries), respond to quarterly data quality reports within 30 days, participate in annual network meetings, and obtain IRB authorization that explicitly covers PCORNet participation. The PCORNet DRN Participation Agreement is a binding legal contract; non-compliance can result in removal from the network and financial penalties under the grant terms.

**NIH N3C** (National COVID Cohort Collaborative) operates under a unique governance model: data contributors execute the N3C Data Use Agreement, which grants the National Center for Advancing Translational Sciences (NCATS) the right to harmonize and reuse the data for COVID-19-related research. The N3C enclave is a controlled research environment operated by NCATS at the Research Data Commons; researchers must obtain N3C-specific DUA access and may not download any record-level data outside the enclave. Organizations participating in N3C should verify that their IRB protocol covers N3C data contribution and that the N3C DUA was executed by an appropriate institutional official (typically the VP for Research or designee).

**Business Associate Agreements (BAAs)** with industry partners require particular scrutiny. The nine required elements of a compliant BAA (45 CFR §164.504(e)(2)) include: (1) established permitted uses/disclosures, (2) prohibition on use/disclosure not permitted/required by agreement, (3) use of safeguards to prevent unauthorized use/disclosure, (4) reporting of unauthorized use/disclosure, (5) ensuring subcontractors agree to same restrictions, (6) making PHI available to the individual (if BA maintains a designated record set), (7) making PHI available for amendment, (8) making PHI available for accounting of disclosures, (9) making internal practices available to HHS for audit. Many industry-drafted BAAs omit elements (6), (7), and (8) — privacy officers must review every BAA against this checklist before execution.

### Branch 4: Governance & Compliance — Extended Compliance Analysis

The Governance & Compliance branch is the normative superstructure that justifies and constrains every other branch. Without effective governance, technical controls become performative — present in documentation but ineffective in practice.

**COBIT 2019** provides the most comprehensive IT governance framework applicable to healthcare research data architecture. The five domains (EDM, APO, BAI, DSS, MEA) map cleanly to the NIST Cybersecurity Framework (CSF) functions (Govern, Identify, Protect, Detect, Respond, Recover) and to HIPAA's administrative, physical, and technical safeguard categories. The COBIT Design Toolkit (available from ISACA) enables organizations to tailor their governance framework to their specific context — enterprise size, risk profile, IT complexity, and regulatory environment. For a healthcare research organization, the highest-priority COBIT objectives are: EDM01 (Governance Framework), APO12 (Risk Management), APO13 (Security), DSS02 (Incidents), DSS05 (Security Services), and MEA02 (System of Internal Control).

**The FAIR Principles** (Findable, Accessible, Interoperable, Reusable) represent the research data community's articulation of what good data stewardship looks like. The NIH Data Management and Sharing Policy (NOT-OD-21-013, effective January 25, 2023) explicitly references FAIR principles and requires that DMS Plans include: (1) data types, volumes, and formats; (2) related tools and software; (3) standards for data and metadata; (4) data preservation, access, and associated timelines; (5) access, distribution, or reuse considerations (including privacy protections); and (6) oversight of data management and sharing. Organizations that align their data architecture with FAIR principles — particularly by assigning persistent identifiers (DOIs) to datasets, using standard clinical terminologies, and depositing data in discipline-appropriate repositories — will have a structurally easier path to NIH DMS Policy compliance.

### Branch 5: Standards & Interoperability — Extended Compliance Analysis

The Standards & Interoperability branch is the technical implementation layer — where governance principles are instantiated as concrete technical specifications. Without standards adherence, the architecture cannot achieve federated interoperability regardless of how well-governed the organizational processes are.

**Zero Trust Architecture (ZTA)** (NIST SP 800-207) represents the most significant paradigm shift in security architecture since the adoption of perimeter firewalls. ZTA rejects the implicit trust model ("inside the network = trusted") in favor of continuous verification of every access request — regardless of network location. For healthcare research, ZTA is particularly important because the research environment spans multiple institutions, cloud environments, and user devices. The CISA Zero Trust Maturity Model v2.0 provides a five-pillar framework (Identity, Devices, Networks, Applications/Workloads, Data) with three maturity levels (Traditional, Advanced, Optimal). Organizations should target the Advanced level for the research data environment, with the Optimal level for the most sensitive systems (e.g., the IRW, the MPI). Key ZTA capabilities to implement: device health attestation (only organization-managed or health-verified devices can access research data), continuous session monitoring (abnormal access patterns trigger re-authentication), and micro-segmentation (the IRW, CDM, and External Hub are separate network segments with explicit allow rules — no implicit east-west trust).

**FHIR Bulk Data Export** (HL7 Bulk Data Access IG v2.0) enables efficient extraction of large patient populations for research and public health use cases. The ONC Final Rule at §170.315(g)(10)(E) requires EHR developers to support Bulk FHIR export. For research use, Bulk FHIR export should be treated as a high-privilege operation: only system-level OAuth 2.0 clients (not user-level) should have bulk export authorization, every export job must be logged with timestamps and client identity, and exported NDJSON files must be immediately encrypted (AES-256) before storage. Organizations should implement a Bulk FHIR export policy that specifies: authorized use cases, approval workflow, retention period for export files, and destruction procedures.
